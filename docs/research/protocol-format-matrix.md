## 0. Corrections and new findings against the three earlier notes (read these first)

1. DCP is not "VC DM 1.1 JWT only". DCP v1.0 defines two profiles: `vc20-bssl/jwt` (VCDM 2.0, Bitstring Status List, JOSE enveloped proof) and `vc11-sl2021/jwt` (VCDM 1.1, StatusList2021, JWT external proof). Catena-X CX-0018 only says "DCP version 1.0" and CX-0050 uses VCDM 1.1 field names; no Catena-X text read names the profile alias (M-60 to M-66).
2. OID4VP 1.0 Appendix B.3.7 defines "SD-JWT VCLD": an SD-JWT VC with an optional `ld` claim holding compact JSON-LD, usable wherever SD-JWT VC is named in OID4VP. The earlier notes say SD-JWT VC has "no @context"; true for SD-JWT VC itself, but OID4VP has a JSON-LD carrying extension inside the same format identifier `dc+sd-jwt` (M-12).
3. ETSI TS 119 472-3 Annex B and 472-2 Annex C extend the OpenID4VC format identifiers: JSON-LD VC secured with JOSE = `vc+jwt`, with SD-JWT = `vc+sd-jwt` (issuance), `vp+jwt` (presentation DCQL), and X.509 attribute certificate = `x509_attr`. None of these is in OID4VCI Annex A or OID4VP Annex B. Naming trap: `vc+sd-jwt` (JSON-LD VC with SD-JWT) is not `dc+sd-jwt` (SD-JWT VC) (M-20 to M-24). This is an existing example of the "extension module" pattern.
4. Commission Annex point 11(2)(a) (read today, SRC-EBW-ANNEX-CELLAR) says "designate one qualified electronic registered delivery service". The words "designate the protocol" are in the Council text (ST 9684/26 Annex 11(2)(a)). DEC-07 note A1.11 quotes only the Council wording (E-13, E-14).
5. In the OJ text of CIR 2026/1731 as held locally (/tmp/w/cir1731.xhtml), the sentence that EUDI Wallets "should also support" W3C VCDM "when the new profiles on the W3C VCDM format are available" sits in the second paragraph of recital (1), not in "recital 18" as dec-01 and dec12 notes say. To verify against the OJ numbering (M-26).
6. RFC 9901 Appendix A.4 "W3C Verifiable Credentials Data Model v2.0" exists (non-normative example). The rb-gln rulebook claim cited in dec-01 B5 is therefore consistent with the RFC (M-81).
7. ETSI profiles for OID4VCI/OID4VP (472-3 Annex B, 472-2 Annex C) cover enveloping proofs only (JOSE, SD-JWT). Data Integrity embedded proofs appear only in TS 119 472-1 clause 7.6.5 and have no OpenID4VC profile in ETSI text read (M-24).
8. OpenID SIOPv2 is still "draft 13" (28 Nov 2023) on the openid.net page fetched today; OID4VP 1.0 lists it under "Pre-Final Specifications" (M-17, M-15).

## 4. Answers

### 4.1 Which formats can be carried by which protocols

1. OID4VCI 1.0 and OID4VP 1.0 are the only two protocols read that define format profiles with identifiers: `dc+sd-jwt`, `mso_mdoc`, `ldp_vc`, `jwt_vc_json`, and (issuance only) `jwt_vc_json-ld`. Yes to the question "do they define credential format profiles for ldp_vc, jwt_vc_json, dc+sd-jwt, mso_mdoc": yes for all four, in App. A (OID4VCI) and App. B (OID4VP). `jwt_vc_json-ld` has an OID4VCI profile but no OID4VP B subsection. Neither defines a VCDM 2.0 plus VC-JOSE-COSE identifier (`vc+jwt` is only in ETSI TS 119 472-3).
2. HAIP 1.0 narrows to SD-JWT VC and mdoc ("at least one of"); it excludes `ldp_vc`, `jwt_vc_json` and the ETSI JSON-LD ids by omission.
3. The EU profile (CIR 2026/1731 -> ETSI TS 119 472-1/-2/-3) adds JSON-LD VC with JOSE or SD-JWT (`vc+jwt`, `vc+sd-jwt`, `vp+jwt`) and X.509 AC (`x509_attr`) as OID4VC extension ids, but the legal list is clauses 2 to 6 of 472-1 (SD-JWT VC, mdoc). The JSON-LD clause 7 is outside that list (M-25).
4. DCP does not define "VC DM 1.1 JWT only". It defines two profiles: VCDM 2.0 JOSE and VCDM 1.1 JWT; custom profiles are allowed ("Profile Authoring Recommendations", M-62). No SD-JWT VC or mdoc profile exists in DCP. It follows that an EU-list credential (SD-JWT VC or mdoc) cannot be presented over DCP without a new DCP profile or a re-issued VC-JOSE-COSE credential.
5. DSP carries no credentials; identity is delegated to a profile (DCP). Catena-X adds CX-0050 schemas and requires DCP 1.0.
6. DIDComm v2.1 carries arbitrary attachments (any `media_type`, `format` hint, optional detached JWS). The application protocols Issue Credential 3.0 and Present Proof 3.0 register only LD Proof VC, Indy-style (AnonCreds-origin) and DIF Presentation Exchange/Credential Manifest formats; SD-JWT VC and mdoc rows do not exist. A registry row could be added without a protocol version change (M-42). WACI-DIDComm restricts to `ldp_vp`.
7. ERDS (EN 319 522 AS4 binding) and CEF eDelivery AS4 carry any user content typed by `ContentType`; they define no credential semantics. Any credential format can be an opaque payload; the evidence, signature and seal are ERDS-level, not format-level.
8. A2A carries any media type in `Part` (`raw`, `url`, `data` + `mediaType`); security is OAuth/OIDC/mTLS/API key; Agent Card is JWS-signed (RFC 7515 + JCS). No credential format profile. ANP authenticates by DID plus HTTP Message Signatures; no VC defined. MCP authenticates by OAuth 2.1 tokens.

### 4.2 What an "extension module" would have to add, per protocol

An extension module here means a pluggable component that maps one credential format (and its status and holder-binding mechanism) onto one protocol.
